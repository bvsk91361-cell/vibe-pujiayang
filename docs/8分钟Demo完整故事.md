# 借一下 Borrow Lab · 8分钟Demo完整故事

定位：Borrow Lab 是面向高校实验实训与校园创作场景的共享设备智能预约平台。

一句话：借一下 Borrow Lab，帮助高校学生快速找到合适的共享设备、查询真实空闲时段，并完成无冲突预约。

故事名：**一次校园采访，设备如何真正就位**。

本文件是操作稿与时间预算，不代表本人已经完成计时彩排。实际耗时、故障和本人验收须填写到 `docs/Demo彩排.md`。课堂反馈、成绩和正式路演结果均不得提前填写。

## 演示前准备

在项目目录运行：

```powershell
node scripts/demo-day.js
```

打开 `http://localhost:3005/#workspace`。默认每次启动创建 `data/demo/` 下一个新的、明确标注的演示数据库；正常使用的 `data/borrow-lab.sqlite` 和用户历史不受影响。要延续某一次演示，仅复用控制台实际打印的路径：

```powershell
node scripts/demo-day.js --db data/demo/实际打印的数据库文件名.sqlite
```

不要将正式数据库传给 `--db`，不要通过删除真实数据或改系统时钟准备演示。端口占用时核查原有演示进程，停止自己启动的旧演示实例；不用强杀其他服务。

上台前用真实页面核对以下事项：

- 身份为“演示学生A”；另一个独立窗口准备“演示学生B”。头像 → 个人空间 → 个人偏好 → 账户 → 管理本地身份，可切换。两窗口各自确认当前姓名，避免刷新后沿用浏览器共享的最后身份。
- 从当天实际日期选“明天 · 14:00–16:00”，核对校园采访组合可预约。若该演示库已被使用，创建新演示库或选择真实空闲时段，不假定永远空闲。
- 给B预先打开同一件设备、同一天、同一时段的确认页，等“正在核对空闲时间”结束，暂不提交。A提交后再让B确认，可展示服务端对过时空闲信息的409拒绝。
- 新生成一次运营周报，核对统计窗口、总量与占用率，并准备真实成功记录供上游断网时查看。只展示已生成的记录，不冒充现场模型成功。
- 1920×1080为主显示尺寸，兼容1366×768；正文可读，通知、搜索、X清晰。不在投屏中打开 `.env`、密钥或Authorization。

演示台账会包含标注 `demo:true` 的时间状态夹具。过去记录通过独立演示库预置，不能声称是通过预约接口成功提交的过去日期。**只有真实当前时间落在09:00–11:00、14:00–16:00、19:00–21:00之一时，脚本才生成“使用时段中”示例。**在营业时段外演示时，如实说明当前没有使用中记录，展示真实时间边界测试，不伪造页面状态。

### 主线操作的两个细节

1. 校园采访目前默认包含云台相机、无线麦、补光灯、三脚架，共4件，属于真实目录推荐。直接借4件最省步骤；若只讲3件，可以通过“调整搭配”移除补光灯，再预约。预置“校园采访 · 演示”是另一个独立保存的三件方案，不能把它的设备与场景默认组合混为一谈。
2. B在A成功后才首次进入预约页，前端会提前展示冲突并禁用提交，这是正确行为。要现场展示后端409，使用B先预读、A先提交、B后提交的双窗口顺序；若无法稳定展示，用实际跨进程HTTP测试结果说明服务端保护，不能把没有发送的请求描述为已返回409。

## 周报数字如何现场核对

本周按周一至周日计算，页面列出的日期窗口是核对依据；热力图是从当天起未来七天，二者窗口不同，不直接拿总数互相比较。

2026-10-08 20:56核验过的“6条预约”仅属于当时那次演示库快照。启动时间、是否处于营业时段、是否跨周、随后新建或取消预约，都会改变有效数量。正式演示必须以当前库及当前生成结果为准，讲稿不固定报6条。

当前26件可运营设备，各有7天×3时段的计划容量，共546个设备时段；2件维护设备不纳入容量。报告不统计拒绝请求次数，也不虚构真实领用时长。示例中的“7/21=33.3%”仅解释计算方式，不声称当前设备一定有7条预约。

## 十个答辩回答

以下每项约20–40秒，按问题选用，不全部塞入8分钟主线。

1. **为什么选择这个项目？** 高校实验实训和校园创作都需要共享设备。学生真正遇到的是不知道借什么、什么时候有空和多人争抢，而不是缺少一个填写表单的页面。校园采访这条故事能把设备选择、预约、冲突和取消串成完整问题。
2. **和普通预约表单有什么不同？** 不只收集输入，提交会重新查真实台账，事务和唯一索引保证有效时段不能重复占用；取消能真正释放。场景让新手找到组合，自然语言查空闲和周报基于同一记录源，而不是另造一份数据。
3. **怎样防止重复预约？** 前端空闲只是提示；服务端再次校验。SQLite对equipment_id、date、slot建立仅覆盖active的唯一索引，BEGIN IMMEDIATE事务包住检查与写入。冲突返回409，整套任一件不满足就全部回滚。
4. **两个人同时抢设备怎么办？** 两个旧页面可能都看到空闲，但数据库写事务及唯一约束只放行一个。实际两进程、两连接12请求只有1个201和11个409，同槽有效记录1条。不是仅靠JavaScript按钮禁用；旧页面提交也有后端保护。
5. **取消后如何释放时段？** 所属身份取消后，记录保留为cancelled，退出active唯一索引。其他身份就能预约同槽。接口和浏览器都验证了A取消、B重约；缺身份、错身份和重复取消不会擅自修改记录。它是本地身份方案，尚非公网认证。
6. **为什么选择SQLite？** 当前是单机课程展示，SQLite有真实持久化、事务和索引，又不需要另外维护数据库服务。它足以验证并发唯一性和重启保留。多进程安全已经测试；未来多机联网需要正式认证和适合部署规模的数据库，不把本机模式冒充云端系统。
7. **AI会编造空闲时间吗？** 模型不决定空闲。明确设备和时间走业务解析；复杂需求调用模型，但输出设备ID必须在真实目录中，日期与时段也校验。服务端按SQLite记录计算结果，提交时再检查；指代不明就请用户选择设备。
8. **周报数据从哪里来？** 本周一至周日的有效预约来自SQLite；程序算热门设备、高峰、低预约和占用率，模型只能组织这些事实及有依据的建议。没有预约或样本少会明确说明，不虚构长期趋势、冲突次数或实际使用小时。
9. **什么是预约占用率？** 一件可运营设备一周7天、每天3时段，容量21个。假设其中7个有有效预约，占用率为33.3%。这是计划占用，不是实际领用时长；维护设备排除容量，取消不再占用，没有领用归还记录就不能声称实际使用率。
10. **AI帮你开发了什么，你自己验证了什么？** 我独立负责需求、取舍和验收标准，AI工具辅助编码、审计、测试与材料整理。验证不靠AI口头保证，而看真实数据库约束、跨进程结果、浏览器点击、实际模型输出和对应Git/CI证据。本轮自动验收由工具执行，本人现场讲解与最终人工验收仍需实际完成。

## 故障路线与时间止损

| 现场问题 | 立即操作 | 必须如实说明 |
|---|---|---|
| 模型超时、余额或上游异常 | 保留问题，不连续发送；改走明确日期设备的本地查空闲；周报展示已生成的真实结果 | 规则查询不是模型成功；已有周报是历史输出，标出窗口与生成时间 |
| 外网断开 | 保持localhost:3005，走设备→预约→冲突→取消；复杂AI部分转真实历史证据 | Node和SQLite不依赖外网；不宣称离线运行DeepSeek |
| 公网旧站打不开或与本地不同 | 使用隔离本地入口，不切到旧静态站充当最新版 | 本轮未部署，旧站不能证明当前SQLite/AI能力 |
| 日期过期、演示库已被借满 | 选择真实空闲的未来日期，或重新启动脚本生成新演示库 | 不改时钟，不清正式库；新库明确是演示数据 |
| 不在任何营业时段 | 展示待使用与已到期页面，补展示开始/结束边界测试 | 当前没有真实“使用时段中”记录，不能假造即时状态 |
| 双窗口冲突步骤未预读成功 | 展示页面真实冲突，打开两进程并发结果 | 前端提前拒绝与服务端409是两层保护，不混称 |
| 页面缓存或状态不一致 | 先确认地址与身份，再刷新记录/页面；重新选择同一目标 | 不盲目清空localStorage、SQLite或用户草稿 |
| 端口被占用 | 使用已经确认是本项目的演示实例，或结束自己的旧实例后重启 | 不强杀别人的服务，不切换到错误数据库 |

**45秒模型段的止损点：**周报现场等待超过约15秒就切历史真实周报，不再重发；保留错误状态供后续排查。最终8分钟成绩以本人完整计时为准，脚本耗时、API耗时和讲稿预算均不能代替本人路演实际用时。
